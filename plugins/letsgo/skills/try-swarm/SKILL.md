# letsgo: try swarm

遵守[语言约定](../letsgo/references/language.md)；其他规则按[letsgo 规则入口](../letsgo/SKILL.md)命中时读取。

评估当前需求是否适合采用宿主原生的**多智能体协同**，适合时采用、不适合时不采用。本技能只决定是否使用 swarm，不决定任务执行节奏（是否停下来征求确认、是否直接实施等由需求本身和其他规则决定）。

## 确定任务

1. 调用消息给出需求或任务时，评估该任务。
2. 调用消息未附带需求时，评估当前对话上下文中已讨论待实施的任务；当前对话也无待办任务时，只问一句“请提供需要评估的任务”。

## 评估准则

以**加快实施**为目标，评估标准放宽；在可采用可不采用的临界情形下**优先采用**：

- **判定为适合**（满足其一且预期能明显缩短用户等待时间）：
  - 可拆出 **≥2 个无写冲突的并行修改面**（如跨模块或跨文件实现、前后端或多端同步改动、代码实现与文档或配置同步更新）；
  - 可拆出 **“主线实现 + 并行只读调研／测试编写／独立代码审查”** 的协同分工；
  - 涉及 **多模块检索测绘、多维度问题排查或批量独立改造**。
- **判定为不适合**（命中其一即不启用多智能体）：
  - **提速不明显且会消耗过多 Token**：单智能体几步内即可快速完成，派生多份独立上下文带来的 Token 倍增与协调耗时超过并行收益；
  - **单点微改、单条命令或纯问答**：无有效并行拆分面；
  - **强顺序耦合且写同一批文件**：后一步强依赖前一步产出，无法划出无冲突写边界，也拆不出有价值的并行只读或验证旁路。

## 宿主原生多智能体映射

按当前运行的宿主客户端选用对应的原生机制：

- **Codex**：利用 `multi_agent_v2` 原生并行子代理工具（`spawn_agent`、`send_input`、`wait_agent` 等）并发派发子线程；代码审查等旁路优先选用已配置的自定义角色（如 `reviewer`）。
- **Claude Code**：利用 **Agent Teams**，由当前主会话作为 Team Lead 拆解任务、建立共享任务列表并生成独立上下文的 Teammates 并行协作；当前环境未开启 Agent Teams 或仅需轻量只读并发时，使用原生并行 `Task` 子代理。
- **Antigravity**：利用原生 **`swarm` 工具**（设置 `title`，按读写隔离需求选用 `workspace: "inherit" | "share" | "branch"` 并 `add` 多个 worker 协同；需展示概览面板时配合 `swarm_pane`）；轻量只读或独立子任务也可直接并行调用 `invoke_subagent`。

## 报告

简洁一行：

- **适合**：“【swarm】采用 `<当前宿主机制>` —— `<一句话分工>`”
- **不适合**：“【swarm】不采用 —— `<一句话原因>`”

报告后不额外等待确认，让任务按其自身节奏继续。

## 协作约定

判定采用多智能体协同后，除不同智能体不得同时修改同一批文件并由主智能体汇总结果外，遵循以下约定：

- **防 stall 误报**：worker 发起预计超 1 分钟的后台长任务（如编译、测试、`gh run watch` 等）前，先在共享消息板发一条不含 `@` 的简短状态备忘（说明执行中的任务）；coordinator 收到 monitor 的 `[stall]` 通知时，先核查活跃成员与后台长任务进度，再决定是否干预。
- **大型跨仓并行审查**：当 ≥3 个大型多端仓并行推进时，推荐拆分 2 位独立 verifier（例如按 Web/Server 与移动端/文档分流），避免单一审查排队瓶颈。
