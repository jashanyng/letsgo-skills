# 编程改动由用户选择验证深度

> 状态：已被 [ADR-0017](0017-minimal-plugin.md) 取代。

2026-11-11 决定：改动编程项目的源代码、构建配置或依赖时，智能体在动手前给出至少三个验证深度选项（推荐级别、比它轻和比它重的相邻适用级别），由用户选择后才实施。验证深度共九级，以移动端 App 的含义为准，其他项目按对应含义解释：静态验证、单元测试、编译构建、冒烟测试、集成测试、功能验证、核心验证、完整回归、灰度观察。选定一级即执行该级及项目已有、适用的更轻级别。规范来源是插件内的 `_rules/spec/references/verification-depth.md`，它取代此前“验收方式”中按静态检查、lint、运行应用逐级递增的笼统说法。

验证做到哪一步决定了耗时与风险，以往由智能体自行决定，结果因对话而异；用户也无法事先知道“验证通过”具体指什么。把级别命名并交给用户选择，使验收标准在实施前就明确且可复查。

## Considered Options

- **智能体按风险自行决定**：不打断用户，但验收深度不可预期，与用户对“完成”的理解常有偏差。
- **只为移动端项目定义**：定义最精确，但其他编程项目又回到无标准状态；改为以移动端为准、其他项目按含义映射。
- **`oneshot-completion` 免于询问**：保持一次授权不等待，但违背“必须由用户选择”的要求；最终让它只在这一处停下。

## Consequences

- `oneshot-completion` 在需求明确时也会为验证深度停下一次；用户在调用时已指定深度则不停。
- `tell-me` 不询问，把推荐级别与做法写入指导。
- 普通对话依靠 `conventions` 命中“改动编程项目代码”场景，命中不能保证。
- 灰度观察需要真实用户，智能体只准备发布与观测清单，结果由用户反馈。
