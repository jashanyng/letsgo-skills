# 需求类型、交付方式与任务流程

> 状态：已被 [ADR-0017](0017-minimal-plugin.md) 取代。

2026-11-11 决定为 letsgo 插件建立插件设计原则：每个需求先归入一个需求类型（五个类型分组下共十六个），交付方式由用户显式调用的技能决定（方案先行、自主完成、逐步推进、说明指导、脚本交付），所有显式技能共用由需求分析、方案设计、方案实施三个流程阶段组成的任务流程。规范来源是插件内的 `_rules/references/task-taxonomy.md` 与 `_rules/references/task-flow.md`，后者取代原 `approval-workflow.md` 与 `task-identification.md`。插件的每次修改都必须遵守这些名称，并用它们表达规则的适用范围。

此前技能按“调用了哪个入口”区分处理方式，没有对需求本身分类，规则只能写成“修复类任务”“普通任务”等临时说法，后续修改难以说清对哪些需求生效。把“这件事是什么”与“怎么做”拆成两个正交维度后，类型决定流程裁剪与验收方式，交付方式决定互动与授权节奏，两者都可以独立扩展。

## Considered Options

- **只按入口技能区分**：维持现状最省事，但同一入口里的讲解、修复与部署无法分别约束。
- **把“操作指导”等交付方式也当作需求类型**：会让同一件事因做法不同而有两个类型，分类失去唯一性。
- **每个需求类型配一套流程**：控制最细，但十六套流程难以维护；按类型分组裁剪即可覆盖差异。

## Consequences

- 显式技能在需求分类后报告一行分类行；专用技能报告登记表中的固定值；普通对话不报告。归不进类型时报告“未归类（自拟名）”并继续，只有长期保存的 Obsidian 笔记不允许未归类。
- 第三个流程阶段命名为“方案实施”，与用户的授权口令“开始实施”区分。
- obsidian-note 的笔记类型改用需求类型并新增 `group`，正文模板按类型分组选择；旧笔记不批量迁移。
- `scripts/validate.py` 校验技能登记表覆盖全部技能、取值属于规定集合，以及入口技能引用任务流程。
